# Changelog

## 0.22.0

`dtk init --global` now connects every agent that it finds, as `rtk init -g` does for its agents, and four more agents were added. No reader changed: compared with 0.21.0 over 6,110 real files (the big results of a 60-day history and the text files of the projects on this machine), nothing is read differently.

- **One command for everything.** `dtk init --global` registers dtk with Claude Code (as before, chained to rtk) and with each of these agents that it finds on the machine (the agent's folder exists, or its program is on the `PATH`): Codex CLI, Gemini CLI, Copilot CLI, Mistral Vibe, OpenCode, Kilo Code, Pi and Hermes. `dtk init --uninstall` takes dtk out of all of them. `--claude-only` keeps to Claude Code, and `dtk init --agent NAME` does one agent. Each file keeps the settings and hooks that it had (a memory tool's, an audit hook, other plugins), a backup is made once, and running the command again changes nothing. One agent that cannot be changed (a settings file with a mistake in it) is reported with exit code 1, is not touched, and does not stop the others. With no `~/.claude` folder, dtk makes none; with no agent at all, it changes nothing and says so (it used to fail). The installers (`install.sh`, `install.ps1`) now run `dtk init --global` on any machine, not only when `~/.claude` exists; `DTK_NO_INIT=1` still skips it. `dtk doctor` names each agent that has no dtk and says `Run: dtk init --global`.
- **Four more agents.** Mistral Vibe (`post_tool` hook in `~/.vibe/hooks.toml`, in a block that dtk marks with `# dtk:start` and `# dtk:end`; Vibe reports the status `success` for a shell command that failed, so dtk reads the exit code in the output and leaves a failed command alone). Kilo Code (a fork of OpenCode: the same plugin, in `~/.config/kilo/plugin/`). Pi (an extension in `~/.pi/agent/extensions/`, event `tool_result`). Hermes (a plugin in `~/.hermes/plugins/dtk/`, hook `transform_tool_result`; Hermes loads a plugin only when it is enabled, so dtk runs `hermes plugins enable dtk` when `hermes` is on the `PATH`, and says the command when it is not). The OpenCode, Kilo, Pi and Hermes shims all call `dtk hook plugin` (`dtk hook opencode` is the same), so the decision is the one function that every agent uses.
- **Works with rtk in each of them, tried with the real rtk 1.1.0.** In Codex CLI, Gemini CLI, Copilot CLI and OpenCode, rtk has only hooks that run before a tool (it rewrites the command), and dtk's run after it, in other entries or files. After `rtk init` for each, `dtk init --global` kept every rtk entry; after dtk, `rtk init` again and `rtk init --uninstall` kept every dtk entry; and `dtk init --uninstall` after rtk kept rtk's. When rtk cuts an output, dtk reads rtk's saved copy in every agent: `tests/rtk_compat.rs` has the real rtk cut a 260-test log and hands it to each adapter in that agent's own event; each digest still covers the failure that rtk cut.
- **Agents that cannot do it.** Cline, Windsurf, Factory Droid and Cursor (for a shell command) have hooks that, by their documentation, cannot replace what the model sees after a tool ran. `docs/HARNESSES.md` lists them and what to use (`dtk run`, a rule). Kimi CLI, Antigravity, Trae and Oh My Pi were not found in the documentation either way.
- **What was tried with the real program, and what was not.** Claude Code and OpenCode 1.18.29: with the real program (see below). Codex, Gemini, Copilot, Vibe, Kilo, Pi and Hermes: written from each agent's documentation, read for this release; none of the programs was run. The code of the Pi extension and of the Hermes plugin is run (with Node and with Python) as each agent calls it, for the cases that a model rarely produces: an error result, an image, a failed command, a broken or slow `dtk`, no `dtk` on the `PATH`.
- Checked by: `tests/agents.rs` (a busy machine with Codex hooks, Gemini settings and a Vibe hook of the user's own: connected, again with no change, uninstalled back to the exact original; only Claude Code; a machine with other agents and no Claude Code; a broken file that does not stop the others), `tests/harness.rs` (Vibe, and every fixture of the corpus giving each agent the same summary), `tests/pi_extension.mjs`, `tests/hermes_plugin.py`, the real-rtk test for every adapter, `dtk verify` (45 checks), and `WITH_RTK=1 scripts/opencode-test.sh`.

## 0.21.0

dtk for any agent harness, not only Claude Code. No reader changed: compared with 0.20.0 over 7,630 real files, nothing is read differently.

- **Four more agents, with the hook or plugin that each one has.** The decision is the one function that Claude Code's hook uses (`hook::handle`), so the rules, the settings, the saved files, the `dtk where|top|rows|get|html` commands, the log of decisions and the guards are the same. Each agent gets a thin translation of its event and its reply (`src/harness.rs`): Codex CLI (`PostToolUse`, the summary is returned as the feedback that replaces the result), Gemini CLI (`AfterTool`, a `deny` whose reason replaces the result, with Gemini's own `Command:` and `Exit Code:` lines kept around the output), Copilot CLI (`postToolUse`, `modifiedResult`, in both of its spellings of the fields) and OpenCode (a plugin on `tool.execute.after`, for `bash` and for MCP tools). `dtk init --agent codex|gemini|copilot|opencode` writes the file. A file that already holds hooks keeps them (your memory tool's, for example), a backup is made once, running it twice changes nothing, and `--uninstall` takes out only dtk's entry. `dtk doctor` names the installed agents that have dtk.
- **`dtk run -c 'CMD'` and `CMD | dtk filter`**, for any agent that has no hook that can replace a result. They run the command (or read standard input) and print what the hook would have put in its place. What dtk leaves alone comes out byte for byte: output that is not data, rows that were asked for exactly (`head`, `sed -n`), output that is not text, `DTK_DISABLED=1`, the shadow mode. The exit code is the command's, a failed command shows its output as it was, stderr goes straight through. `--request TEXT` or `DTK_REQUEST` gives the words of what the user asked.
- **A rule for agents that have only rules.** `dtk init --agent rules` puts a block in `AGENTS.md` (or `--file PATH`) that tells the model to run data-printing commands through `dtk run`; `dtk init --agent cursor` writes `.cursor/rules/dtk.mdc`. This is not automatic, and the command says so: Cursor's hooks can replace the output of an MCP tool only, not of a shell command.
- **dtk does not rewrite commands by itself, on purpose.** Several agents can rewrite a command before it runs, and it could become `dtk run -c '...'`. The text of the command is what an agent's allow and deny rules read: a rule such as "deny `rm *`" would stop matching, and an agent in an automatic mode would run it. A hook that replaces the result after the command ran changes no permission. `docs/HARNESSES.md` has the reasons and the steps for each agent.
- **What was tried with the real program, and what was not.** Claude Code: every release. OpenCode 1.18.29: with the real program and a real model (one of its free ones), the bash tool returned dtk's summary (218 tokens instead of 2,050) and the model answered right; `scripts/opencode-test.sh` repeats it. The plugin's code is also run as OpenCode calls it, with Node, for the cases that a model rarely produces (an MCP result, a broken or slow `dtk`, no `dtk` on the PATH). OpenCode 2.x (the `setup()` entry of the plugin) is written from the documentation and tried only that way: the real 2.2.6 gave no events in a clean environment. One thing the test showed: with the desktop CLI of 2.2.6 and the usual configuration, rtk's own OpenCode plugin rewrote `cat orders.csv` to `rtk read orders.csv`, and that rewritten text no longer matched a permission rule for `cat`, which is the reason dtk does not rewrite commands. The Codex, Gemini and Copilot hooks were written from each agent's own documentation (read for this release), and are tested with payloads written as that documentation says; none of the three programs was run. If one does not work for you, `dtk skeleton` and the issue template are the way to say so. The README and `docs/HARNESSES.md` state this in a table.
- Checked by: `tests/harness.rs` (documented payloads for each agent, what each must leave alone, and every fixture of the corpus giving each agent exactly the summary that Claude Code gets), `tests/run.rs` (byte-for-byte pass-through, exit codes, signals, stderr, standard input, the answers to `dtk` queries), `tests/agents.rs` (a realistic `hooks.json` with other hooks in it must come out as it went in), 4 new checks in `dtk verify` (44), and `scripts/opencode-test.sh`, which runs the real OpenCode on a real model and reads what the tool returned to it.

## 0.20.0

Summaries that show the row you asked for, and the shapes that real DuckDB, Spark and dbt output turned up. Compared with 0.19.0 over 7,406 real files (30 days of history and every text file of the projects), the only differences are four new fixtures of this release, each an improvement.

- **A summary adds the rows that your request is about.** A model that asks for the status of order 5042 and gets a summary of 300 orders had to take one more step to see that row, and a smaller model often did not take it. dtk now compares the words of the request with the cells of the table: the command, the description that the model wrote for the call, and what you last typed (read from the end of the session transcript, only when it is under `~/.claude`). A row that holds one of the words as a whole cell is added under `matches for words in your request (id = 5042)`, at most 8 rows. Only a text column counts, or a column of whole numbers that are all different, such as an id: the word `3` is not a request for the rows with a quantity of 3. A word that matches more than a fifth of the rows names nothing and is skipped. A table that is shown whole never changes. With no matching word the summary is exactly what it was: a test checks this on all 83 fixtures of the corpus and on a table, byte for byte. The words are not stored. Setting: `request_rows`. The transcript is Claude Code's own file and is not documented: the reading is best effort, and when it finds nothing the command and its description are the request. (The `last-prompt` entry was seen to hold the previous prompt, so it is not used.)
- **Measured with real Claude Code** (Haiku, 3 runs per arm): a question about one row of a wide frame went from 0 of 3 and 1 of 3 right to **3 of 3**; a key lookup in a 300-row CSV stayed 3 of 3 and now needs no extra step (6 turns for 3 runs, where 0.18.0 needed 9). The summary is 14 to 40 tokens longer. All 32 cases of the suite are right with dtk. One case costs more tokens with dtk than without, as it did before: `wide means` (a table of 60 columns) used 840 tokens with dtk against 563 without (3 runs; 0.19.0: 793), because the model reads follow-up output; the answer is right in both arms.
- **DuckDB's box tables.** DuckDB prints the type of each column in a row under the header, and shows a long result cut, with three rows of dots and a line `300 rows (20 shown)`. dtk read the type row and the dots as data: 300 rows were 301, and a column of numbers became text because of a dot. The types are now a note (`column types as printed: id int64, customer varchar, ...`), the dots are rows left out, and the count line stays. Checked against DuckDB's own CSV, cell by cell.
- **Spark.** `df.collect()` prints `[Row(id=1, customer='cust_001', ...), ...]`: it is now a table with the names of the fields as columns (5,874 tokens, 95% smaller). A call whose arguments are all `name=value` is a record, so namedtuples and dataclasses read the same way. `df.show()` was read before, and now has a real fixture. Real Spark prints warnings and a progress bar to stderr; with `2>&1` they come before the table.
- **A wrong table, fixed: words in front of data became column names.** With nine lines of Spark's warnings in front of `toPandas().to_string()`, the second line of the warnings was taken for the header, 305 rows were read, and the columns were called `Using`, `Spark's`, `default`. A header must now be followed at once by rows. Spark, JVM and Python warnings (`.py:127: FutureWarning`, the line of source under it, `WARN NativeCodeLoader`, `[Stage 0:>`) join the noise that may stand before data, and the table is read with its own header. A progress bar drawn over with `\r` (tqdm, Spark) is read as a terminal shows it. A carriage return inside a CSV cell is not touched.
- **A wrong table, fixed: one line of text with a comma before a CSV.** `Loaded the rows, took a while` above a CSV made the reader take the CSV as headerless, the real header as a row of data and the columns as `c0`, `c1`. A first row of names above columns of numbers is a header. The line of another width that was dropped without a word is now a note. This was in 0.19.0 and before.
- **dbt** needed nothing: a real `dbt build` log (one failing test, 123 skipped nodes) is digested from 3,616 to 597 tokens and names the failing test, its cause and `Done. PASS=3 WARN=0 ERROR=1 SKIP=123`. It is now a fixture.
- `dtk verify` has 40 checks (it adds a DuckDB table, Spark rows and the request rows). `dtk explain --request TEXT` shows what a request would add. For programs that use dtk as a library: `lean::render_for` is `render` with the words of a request, and `request` is a new module.
- Checked by: real output of DuckDB, PySpark (with Java 17) and dbt-duckdb as fixtures, with the CSV that made each as the expected value; tests for each guard; the comparison of builds over 7,406 real files; the claims audit on all fixtures; and the full A/B suite.

## 0.19.0

Guards, and a way for anyone to show dtk an output that it should read. No reader changes: dtk reads and summarizes exactly what 0.18.0 does (7,396 real files compared, no difference).

- **A check that a summary only promises what a reader can reach** (`tests/claims.rs`). It runs the real binary on every fixture and checks each promise: "the full data is on disk" names a file and the file exists; the numbers in `N rows x M cols` are the saved CSV's; every `dtk` command in `drill:` and `more:` answers; a saved page can be read. The audit has tests of its own for each kind of broken promise. With the 0.17.0 behaviour put back, it fails on 6 fixtures (`ps aux`, `ps -ef`, two `gh` JSON outputs, a syslog and a correlation matrix), so that bug touched more kinds of output than was known when it was fixed in 0.18.0.
- **`scripts/compare-builds.sh OLD NEW PATH...`** says what two builds make differently of the same files, and fails on a difference that was not expected (`--allow REGEX`). A release lists every difference in its changelog. It is the comparison that was done by hand for 0.17.0 and 0.18.0.
- **`dtk discover --gaps`** lists the big outputs that dtk left alone and that look like neither source code nor prose, grouped by command, with repeats counted. It is a list of places to look, not of faults: on a real 30-day history it found 255 outputs, and many are long log lines. **`dtk discover --dump DIR`** writes the big outputs as files, for `compare-builds.sh`; they are your own output, so keep them private.
- **`dtk skeleton FILE`** prints the layout of an output with every value taken out: each digit is `9`, each lowercase letter `a`, each uppercase letter `A`; punctuation, spacing and line breaks stay, so the columns still line up. The first 40 lines and the last 5 are kept. It also says what dtk makes of the output. Attach it to an issue (there is a template) when dtk should have read an output and did not: no value leaves your machine. `--keep-header` keeps the first line, the column names, as they are.
- Checked by: the claims audit and its own tests; the comparison script run on fake builds that disagree and over 7,396 real files; `--gaps` and `--dump` on a transcript that holds a table, source code, prose and an unread layout; and a test that no letter or digit of any of the 100 fixtures, and of a planted secret, is left in a skeleton.

## 0.18.0

More of the data that data work prints, found by running dtk over every big output of a real 60-day history and over real output of pandas, `sqlite3` and Spark. A comparison of the old and the new build over all 1,745 outputs of that history shows one change: the Spark log below. No output was newly taken for data by mistake.

- **A bug that lost data without a word.** A table of 60 rows or fewer is shown whole as CSV. When that CSV is not clearly smaller than the original (a wide frame of 60 rows: 22% smaller), dtk gave the statistics summary instead. The summary said "the full data is on disk", but dtk had saved nothing and gave no path, so any row outside the head, the tail and the extremes could not be reached. Now the data is saved, and the summary says where and how to read a row. With real Claude Code on Sonnet, a question about one row of such a frame went from not answerable to answered (2 of 2) with 63% fewer tokens.
- **A list of tuples** (what `cursor.fetchall()` prints, also through `pprint`). `datetime.datetime(2025, 3, 1, 8, 52, 1)`, `datetime.date(...)` and `Decimal('597.94')` are read as dates and numbers, so the summary has a date range and a mean. The columns are called `c0`, `c1`, ..., and the summary says that tuples have no names. 240 rows from `sqlite3`: 7,185 tokens became 411; the counts, the range of dates, the nulls and the mean match a count made in Python.
- **A wide pandas frame printed in blocks of columns** (`pd.set_option("display.width", 200)`, then `print(df)`, which is what an exploring model does). Each block repeats the rows and ends its header with a backslash. dtk reads each block and joins them row by row, and only when every block has the same rows and the same index label in every row. A named index, which pandas prints on a line of its own under each header, is read too. The result equals the CSV that pandas writes from the same frame, cell by cell (6 real frames, among them a three-block frame, a frame with a named index, and one whose last block holds one column). A frame of 80 rows and 39 columns: 6,804 tokens, 84% smaller.
- **Columns that pandas hid.** With many columns, pandas prints `...` for the middle ones. dtk used to refuse such a frame. Now it reads the printed columns and adds a note: "pandas hid some columns in this output, between region and f22". 300 rows: 4,897 tokens became 467.
- **A frame of numbers with a label in each row** (`df.corr()`, `df.describe()`). pandas puts one space between a label and a negative first value, which broke the reading of every such frame whose first column holds negatives. A 34 x 34 correlation matrix is now read whole.
- **A Markdown table with an index** (`df.to_markdown()`): the blank first header is called `index`.
- **A Spark and Maven log.** Spark's `yy/MM/dd HH:mm:ss` was not a timestamp, and a log in which many lines are stack traces was refused because the stack lines were counted as "not rows" although they belong to the record above. Both are fixed (`13-Jul-2026 22:58:59.123` and `07/13/2026 22:58:59` too). 292 lines, 7,096 tokens became 525, with the two errors and the warning and what happened before them; the stack trace and the Maven result lines stay in the saved copy.
- Measured with real Claude Code (Haiku, with and without dtk, 3 runs per arm for the frames): the hidden-columns frame 3 of 3 right with 61% fewer tokens, the correlation matrix 3 of 3 with 30% fewer, the `fetchall` list 1 of 1 with 93% fewer, the Spark log 1 of 1 with 92% fewer. A question about one row of a frame that got the summary was answered 1 of 3 times by Haiku, which offered to read the saved file instead of reading it, and 2 of 2 by Sonnet, which read it with `dtk where`.
- **`dtk verify` checks all of this on the installed binary:** a list of tuples, a Spark log, a wide frame in blocks of columns, a long build log (digest) and a fetched page now join the other built-in samples (35 checks). Run it after an install on a new machine; it needs no network and no rtk.
- Checked by: real pandas, `sqlite3` and Spark output as fixtures, with `NAME.expected.csv` written by pandas next to each frame (`tests/frames.rs`); a test that tampered blocks (a changed label, a missing row, a missing backslash, a repeated column) are not joined; tests for each refusal of the new readers; the hook test that the data of a small summarized table is saved.

## 0.17.0

The log digest now works without a saved file, and with rtk's cut output. It is on by default.

- **A long log that was not saved gets a digest.** Claude Code saves only an output of more than 30,000 characters. A `pytest -v` run of 5,900 tokens, or a compiler run of 4,900 tokens, went to the model whole. Now a log of about 3,000 tokens or more gets the digest, and the whole log is kept in dtk's store (the digest says where). Setting: `min_digest_tokens` (default 3000; 0 means never).
- **A log that rtk cut gets a digest of all of it.** `rtk uv run pytest -v` keeps about fifty lines and saves the rest. dtk reads rtk's saved copy (the tee file or `rtk recall --full`), as it does for tables, and digests all of it. A run of 260 tests: rtk showed 778 tokens (the first 25 passes and the end); the digest is 690 tokens, covers all 325 lines, and gives the assertion and the line number of each failure. rtk's own pytest filter already keeps the names of the failures, so the gain is larger for a log that rtk cuts without knowing the tool.
- **Same limits as before.** Never for `cat`, `grep`, `find`, `git diff`, `curl` and their kind, and never for an output that has a table. A digest from rtk's cut output is used if it is at most 30% (and 400 tokens) larger than what rtk showed; a digest of a log that rtk did not cut must be at least 50% smaller than the log.
- **No false log in real history.** Of the 1,745 outputs in a 60-day history, 2 outputs of 3,000 tokens or more that are not tables were digested. Both are `cargo build` and `cargo test` logs. The test that no file of this repository that is not a log is digested still passes.
- **Measured with real Claude Code** on three real logs (3,000, 5,900 and 4,900 tokens): every answer was right with the digest and without it, and the cost fell by about 30% to 40%.
- **README:** the safety section said that dtk does not touch MCP tool output. That was wrong since 0.13.0. It now says what dtk reads.
- **`docs/PRINCIPLES.md`** says what dtk is for and the rules for a change: automatic first, full integration with rtk, no silent loss, no model inside dtk, evidence not opinion.
- Checked by: a real log of 260 tests as a fixture; hook tests for a long log that was not saved (the store copy, the commands that must not get a digest, the threshold, the setting off) and for a log that rtk cut; a test with the real rtk binary that cuts a log through `rtk uv run` and checks the digest of all of it; a fresh-home install with and without rtk (`dtk doctor` and `dtk verify` pass in both).

## 0.16.0

Web pages from the two other places they come from: MCP tools and files that are read.

- **MCP tools.** A page returned by a fetch or browser MCP server (`mcp__fetch__fetch`, a "page HTML" tool) becomes its text in the shape it came in (content blocks stay blocks, a string stays a string). An MCP tool that reads files from the disk (`read_file`, `read_text_file`, `get_file_contents`, a `filesystem` server) is left alone, because for an HTML file that may be source being edited. Live pages are not checked for template syntax, because they often hold `{{` in a script or a code sample. `exclude_commands = ["^mcp__fetch__"]` skips a server. Checked with real Claude Code and a test MCP server: a 4,920-token page became 391, with the same answer.
- **Files read with `Read`.** A whole `.html` file that is a page is shown as its text, with a line that says what it is and how to see the markup (read it with `offset` and `limit`, or use `cat`). Left alone: a range, a file under about 10 KB (2,400 tokens, source being worked on), a file with template syntax (`{{`, `{%`, `<%`, `<?php`, Vue and Angular directives, Alpine's `x-data`), and any name that is not `.html`, `.htm` or `.xhtml`. Setting: `html_reads` (it also governs MCP). A 5,144-token file became 467 with the same answer.
- **Edits still work.** The case that could go wrong is a model that reads a big HTML file in order to change it. With real Claude Code on Sonnet, asked to change the `<title>` of a 20 KB page after reading it, the edit was correct and minimal in all four runs (two with dtk, two without). With dtk the model either made the edit directly or looked at the markup first with `Grep` or `Bash`, as the note says, and each run cost about 30% less because the raw page never entered the conversation.
- Checked by: tests for each path and each guard through the real binary (Read, a range, a small file, five kinds of template, another extension, the setting off; MCP in both shapes, three file-reading tool names, a live page with `{{`, a small page, an exclusion); `scripts/mcp-test.sh` and `scripts/tools-test.sh` have a page case each; 252 tests.

## 0.15.0

Two kinds of output that are long and mostly noise: build and test logs, and web pages.

- **A log digest.** Claude Code saves an output of more than 30,000 characters to a file and shows the model its first lines, which in a log are the boring ones. Now a log that is saved gets a digest of all of it: what it is made of (`3200 x compiling *`), every kind of error and warning with the line number of the first, where the others are, and the lines that follow it when a compiler puts the place under the message; how many errors there are and in which files; the first lines and the last twelve, where test runners say how it ended. It is made by counting, not by a model, so it is instant, free and the same every time. A real `pytest -v` run of 13,000 tokens became 650, with `7 failed, 593 passed` and the line of every failure; 80 rustc errors of 13,800 tokens became 660, with each error code counted. The full text stays in the saved file, and the digest says how to read part of it.
- **It is for logs, and only logs.** Source code, documents, diffs, lists of names and results of a search are the lines themselves. A digest needs the output to look like a log in two ways (a few line shapes make up most of it, and most of its lines say something a log says: a level, a timestamp, `Compiling`, `test ... ok`) or to be a pile of diagnostics that begin with `error`, `warning` or `path:12:5: error:`. It is never made for `cat`, `grep`, `find`, `git diff`, `curl` and their kind. Checked against every big output in a 60-day history and every source, document and rejected fixture of this repository: none is taken for a log. Setting: `digest_logs`.
- **A web page becomes its text.** A page fetched with `curl` or `wget` (or a script with an address in it) is 85% to 90% markup: Wikipedia's CSV article is 48,000 tokens of HTML and 2,300 of text. dtk gives the model the page as a person reads it: headings, paragraphs, lists, tables, code, and links with their addresses, without scripts, styles, SVG, hidden elements and the menu (`(navigation menu: 35 links)`). The page is saved, and `dtk html ID text|headings|links|tables|json|grep` reads any part of it, including JSON that the page embeds. A comparison with an independent walk of the page found none of its visible words missing. A page that is a table (`df.to_html()`) is still a table. `cat page.html`, `sed`, `grep` and `Read` are people working on the markup, and are never converted. Setting: `html_pages`.
- **Fixed in the text-log summary:** a timestamped log's error rows were cut to the width of a sample row and gave no way to find them. They are now cut at 170 characters and say which row they are (`row 1201: ...`). Before this a model asked for the first error and its line could only say it was cut off.
- Checked by: real logs from pytest, cargo test and rustc as fixtures, with the facts worked out in the test; a rule that nothing in this repository that is not a log is digested; hook tests for a saved event (digest, the commands that must not get one, the setting); a real web page as a fixture with the words counted by an independent walk; real Claude Code on Sonnet (about 10% cheaper and one turn fewer on logs, and right 10 of 10 where the plain arm was 9 of 10; 31% to 40% cheaper on a page of 5,000 tokens, and 8% to 15% cheaper on pages of 25,000 to 48,000 tokens, saved to a file). Tried and not built: a message suggesting a smaller model, which a model never took in 16 sessions and which cost about 7% more.

## 0.14.0

How dtk meets the tools that Python and CI work runs through: `uv`, rtk's wrapper around it, and the GitHub CLI.

- **rtk cut a script's output to fifty rows; dtk now reads what rtk saved.** rtk's pre-command hook rewrites `uv run python script.py` to `rtk uv run python script.py`, and rtk cuts the output of that wrapper to about fifty lines, with a pointer to the rest. A script that printed an 800-row table reached the model as 50 rows, and dtk, which refuses to summarize output that rtk has cut, could not help either. rtk keeps the whole output. dtk now reads it: the tee file named in `[see remaining: tail -n +26 "$HOME/.../rtk/tee/1_uv-run-stdout.log"]`, or `rtk recall --full HASH` for `[+N hidden: rtk recall HASH]`. A 500-row DataFrame with a datetime column, printed with `uv run`, went from 50 rows in 919 tokens to a summary of all 500 rows in 452. ## 0.11.0

Two wrong summaries, found by testing with the data that data people print. Both are fixed.

- **Small numbers keep their digits.** Statistics were rounded to four decimals, so a column of p-values, rates, losses or learning rates (1e-8 to 1e-3) read `rate: 0..0 mean 0 p50 0 p95 0`: a model would call the column all zeros. Now a number below 0.1 has four significant digits, a number below 1e-4 is in exponent form (`2.96e-8`), and the smallest and largest value are the cells as written (`rate: 2.960e-08..9.983e-06 mean 4.827e-6`). `dtk group` prints the same way. Cost: 20 tokens on a table with five such columns; 0.09% on the whole corpus.
- **pandas output with a MultiIndex is read.** `groupby([a, b]).agg(...)`, a Series from `value_counts()` or `groupby().sum()`, `pivot_table`, `set_index`. pandas leaves a repeated index label blank, so the rows do not have the same number of cells and a split on spaces gives the wrong columns. The new reader works by character position instead: the line of index names marks the index columns, and the right edges of the values mark the value columns. Two or three lines of column names are joined (`amount.sum`, `qty.count`), a blank top label repeats the one to its left, a label with a space (`New York`, `Home & Garden`) stays whole, and the name of a column level (`year` in a pivot table) is not a column. A Series needs its `Name: ..., dtype: ...` footer. A line that does not fit makes the reader refuse the text, not guess.
- **Fixed: a table with a missing column and missing rows.** When the groups were big, the aligned-text reader took the short rows (one blank index label) for the whole table. It dropped the first row of every group and the group column, and the summary still said "statistics over all rows". A 240-row `groupby` was read as 236 rows with no `region`. The reader now refuses a table when a line it would drop has more cells than the rows it keeps.
- Checked by: every value of 20 real pandas outputs (about 11,000 cells, with row counts and header names) compared with the pandas frame they were printed from, none different; 8 new corpus fixtures whose rows and headers come from the pandas frames, and one of tiny values; a test that fails without the fix to the aligned reader; retention 1854 of 1854 (the new fixtures are what found the rounding); three new real-model questions, Sonnet and Haiku 2 of 2 right with and without dtk, 78% to 80% fewer tokens.

## 0.8.0

The analytics a data person asks first, built in so that no other tool is needed.

- **`dtk group FILE BY [MEASURE...]`.** The mean, sum, min and max of each measure per value of BY (`region,tier` for two columns), the biggest groups first. `--agg mean,sum` picks some, `--limit N` caps the groups. It reads `$1,200` and `45%` as numbers and skips `N/A`. Since 0.6.0 the README said `qsv` was not needed, but "mean of X per Y" was the one common question without a built-in answer. The `drill:` line now suggests it.
- **Time columns.** A summary says whether the rows are in time order (`sorted oldest first`, `sorted newest first`, `not in time order`), the step between them (`every 5min`, or `typical step ...` when uneven), and the longest gap when it is more than three steps (`longest gap 3h5min after row 148`). Times are read with their offset (`Z`, `+02:00`) and fractions of a second. Dates alone give `every 1d`.
- **Correlated columns.** Pairs of measure columns with |Pearson r| of 0.9 or more are named, strongest first (`temp_c~temp_f 1.00`). Identifier columns and codes are left out, because a column that rises with the row number correlates with anything that drifts. A table over 100,000 rows is sampled at an even stride.

## 0.7.0

More of the shapes data takes, found by printing a DataFrame every way pandas allows and checking what dtk made of each.

- `df.to_csv()` was not read. It writes the index as a column with an empty name, and the empty header made dtk refuse the file. That column is now called `index`.
- **Python repr.** `print(df.to_dict("records"))` and a dict of lists (single quotes, `True`, `None`, `nan`, `Timestamp('...')`, `np.float64(1.5)`; any other call stays as its text). Valid JSON is never read this way.
- **Columnar JSON.** `to_json(orient="split")` (`{"columns": [...], "data": [[...]]}`, also `headers`/`rows`) and an array of arrays whose first row names the columns.
- **Number grids.** A printed numpy matrix, `np.savetxt`, any rows of numbers with no header (columns `c0`, `c1`, ...).
- **Headerless delimited text.** `psql -t -A`, `sqlite3 -list`, `cut`. There are no names to check, so the cells must show it is data: the same field count on 98% of the lines, three or more fields, a third of the columns numbers. A drawn table (`| 1 | 2 |`) is never read this way.
- **Record blocks.** `psql -x`, `sqlite3 -line` and MySQL `\G`, one block per row; every block must have the same keys.
- **HTML tables.** A page that is one `<table>`, as `df.to_html()` writes it. A full page or two tables is left alone.
- **Dates.** `03/21/2025` and `21.03.2025` are dates when the data settles the order (a part above 12 says which is the month), with a range in ISO form. A column where every part is 12 or less stays text, because a wrong guess would give a wrong range.
- A test that said "numbers only is not a table" now expects a grid of numbers; the fixture moved to the positives on purpose.

- Never summarize the output of commands that ask for specific rows (`qsv slice`, `head`, `tail`, `sed -n`, rtk's `--max-lines` and `--tail-lines`). `DTK_RAW=1` passes one command through.
- Refuse pandas `to_string()` tables when the column labels could be wrong (a datetime column joined to its neighbour by one space). This fixes mislabelled columns.
- `dtk init` now registers the `Bash|Read` matcher. `dtk doctor` warns about registrations made before 0.2.0.
- The rtk chain waits for the chained command with short checks at first (0.2 ms, backing off to 10 ms) instead of a fixed 10 ms sleep.
